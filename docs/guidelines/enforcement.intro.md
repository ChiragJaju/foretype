# Enforcement map

Which check or tool enforces each rule, and why a reviewer enforces the rest.
Where a check covers part of a rule, the row names the check and the note says
what is left to review. A rule marked **review** has no mechanical form yet, or
cannot have one; the note says which.

The tables below are generated by `node scripts/generate-guidelines.mjs`: the
ids come from the rule files, what enforces each from the checks'
`scripts/check-*.rules.json` and from `tool-enforcement.json`, and the notes
from `enforcement-notes.json` ([guidelines.md](../guides/guidelines.md)). Edit
those, never the tables.

## Required checks

Branch protection on `main` requires four checks: `Repo checks`, `Lint`,
`Type-check` and `Unit tests`. Every `scripts/check-*.mjs` runs in `Repo
checks`; SwiftLint, swift-format and oxlint run in `Lint`; `swift build` and the
site's `tsc -b` in `Type-check`; `swift test` and the `node:test` suites in
`Unit tests`. `make verify` runs the same checks locally
([verify.md](../guides/verify.md)).

## Who reviews

Foretype has one maintainer and no review bot, so protection requires checks,
not approvals. "Review" means the maintainer reading the PR against these
rules, after the author ran `/deslop` on the diff. A waiver that would need a
second approver (a budget or baseline that grows) is reported, not blocked,
until a second approver exists.
